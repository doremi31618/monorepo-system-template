# Technical Design Review

讓使用者在實作前理解系統如何改變，並在 Review 時確認實際結果符合已確認的設計。這份文件是共用規範；每個 Work Item 的設計與決策記錄保留在該專案，不能寫回本 reference。

## 使用時機與文件位置

- 每個 Work Item 在「規格先行」階段完整交代下列七項，再進行受影響的實作。只有後端或前端的工作也保留七項，將無關項目標為「不涉及」並附理由。
- 實際內容放在 `docs/system-spec/` 的既有 Technical Spec 檔案或段落，與 Work Item ID 雙向連結；Project Task 只保存規格連結、核准與實作對照紀錄。小型變更可用短表，不另建一套文件空間。
- 沿用已寫清楚的設計時引用對應段落，說明本次使用方式與影響；不用重寫整個系統。只列檔名、service 名稱或「照舊」不足以交代機制。
- 七項都必須說明，但不是每項都需要使用者核准；核准條件見下節。需求已確認或 Grill Me 已完成，不自動代表尚未呈現的技術決策已核准。

## 七項必要說明

每項標示「沿用／修改／新增／不涉及」。同一項可拆列多個子項並分別標示；修改與新增須說明現況、預計變更、理由與影響，不涉及須附一句理由。無法從程式或文件確認的現況應標為待查證，不可猜測。

| 範圍 | 項目 | 必須交代的內容 |
| --- | --- | --- |
| 後端 | API | 使用、新增或修改哪些接口；呼叫方、輸入輸出、權限與錯誤處理。批次或事件功能沒有 HTTP API 時，標示不涉及並說明實際入口。 |
| 後端 | Table / Schema | 讀寫哪些表、相關欄位與關聯、資料粒度及用途；哪些結構改變，是否需要 migration、回填或相容處理。沒有 schema 變更仍須交代涉及的既有表。 |
| 後端 | Service / Mechanism | 業務規則、責任分工與資料流；涉及的快取、同步／非同步、排程、重試、去重或外部整合如何運作，以及相關失敗如何處理。只展開本次涉及的機制。 |
| 後端 | Resources | 沿用、修改或新增的運算、儲存、Job、佇列、外部服務等；用途、環境、規格、執行身分／所需權限與預估增量費用。費用無法估算時列出計價因素與待確認事項，不編造金額、不輸出 secrets。 |
| 前端 | UX 流程 | 使用者從哪裡進入、操作順序與結果；相關的載入、空資料、成功、失敗與恢復流程。 |
| 前端 | UI 元件 | 使用哪些既有元件或 module，哪些需修改或新增，以及選擇原因；引用既有 UI Module Catalog／設計系統，沿用其使用規則。 |
| 前端 | Service / Mechanism | API 串接、狀態歸屬與生命週期、快取、資料刷新、請求順序及錯誤恢復；只說明本次相關行為。 |

Service / Mechanism 說明「怎麼運作」；Resources 說明「靠什麼執行」。例如每日彙整的觸發與處理順序屬於 Mechanism，承載它的 Job、運算設定與執行身分屬於 Resources。

涉及 cache 時，說清楚快取內容、保存位置與共用範圍、TTL／可接受的新鮮度、失效或刷新條件、失敗時行為；涉及帳號或權限切換時也須交代資料隔離與清除方式。前端記憶體快取同樣屬於機制，即使沒有新增雲端資源也要說明。

文字與表格已足夠時不用額外畫圖。跨元件互動、非同步或快取行為難以用短文理解時，補簡單循序圖／資料流圖；資料關聯可用 ER 圖，UX 可用流程圖，不強制完整 UML。

## 需要使用者明確同意的決策

下列情況必須在受影響的實作之前取得同意：

1. **新增資料表**：列出用途、資料歸屬、為何既有表不足、替代方案，以及遷移或回復方式。
2. **變更架構**：相對於已確認的設計，新增或改變服務／模組責任邊界、跨元件資料流或狀態歸屬，或引入／實質改變共用機制。例：同步改非同步、引入快取、改變快取的共用範圍／新鮮度／失效規則、引入前端持久狀態或背景刷新。指出具體改變及取捨，不以「架構優化」概括。
3. **新增資源**：列出新增的可部署或需管理資源、用途、環境、規格、權限、費用與移除／回復方式；沿用既有平台但新建一個 Job、佇列或儲存資源，仍屬新增。

沿用已確認模式且符合其適用範圍、純函式內部整理、命名或不改變上述機制的局部實作，不另設核准要求；仍須交代本次差異。不要把每個函式、新增檔案或 UI 元件都視為架構變更，也不要以程式行數少或未新增資源為由略過機制變更。

請求核准時，提供可供決定的現況與方案、理由、替代方案與取捨、影響／成本／風險、回復方式，並明列待核准項目。可以在一次呈現中合併多個決策，避免重複詢問。若先前已明確同意完全相同的範圍與方案，引用該紀錄，不重新索取相同授權。

將使用者的明確同意內容、日期、決策範圍與對應規格版本／日期記錄在 Project Task。對具體方案的「可以」可作為同意；沉默、測試通過、一般的「繼續開發」或對功能目標的核准不能取代尚未提出的設計核准。此記錄不取代工具或環境本身要求的執行權限。

尚未核准時可以進行唯讀調查、設計草稿及不依賴該決策的工作；不要先做完受影響的程式、migration 或資源配置再補核准。後續方案若實質超出已核准範圍，先更新說明並重新取得該部分的同意。

## 實作對照與 Review

Owner 在 Review 前將七項說明更新為實際結果，保留原核准方案與實際差異的可追蹤紀錄，提供關鍵程式位置及相關驗證證據。無差異也須明記「符合已確認設計」。不要以直接覆寫規格掩蓋偏離。

Reviewer 核對：

- 七項是否完整，沿用與不涉及的判定是否符合實際程式與配置。
- API、資料結構、前後端流程及機制、資源是否符合設計，是否有額外引入的項目。
- 所需核准是否涵蓋實際方案，差異是否已有說明及必要的重新核准。
- 驗證是否涵蓋本次機制的可觀察行為；例如快取失效、重試或失敗恢復，依實際影響驗證，不為填滿七項而增加無關測試。

發現未核准的資料表、架構變更或新增資源時，標為待決策，停止合併，回到具體設計確認；補文件或測試成功不能代替使用者同意。設計審查與 TDD 的行為驗證並行協作，不取代程式碼 review、既有 UI catalog 檢查或 Dev 使用者驗證。

## 精簡輸出格式

在 Technical Spec 使用以下欄位；列齊七項，細節可連到同一份規格的既有段落。

| 範圍／項目 | 沿用／修改／新增／不涉及 | 現況與本次方案 | 理由與影響 | 待核准項目 |
| --- | --- | --- | --- | --- |

表格後只展開相關機制、必要圖示與待決策事項。Project Task 使用 [project-task-template.md](project-task-template.md) 的 Technical Design Review 欄位保存規格連結、核准紀錄與實作對照結果，避免重複維護設計正文。
