# Requirements Discovery Gate（Grill Me）

本文件定義 `add-new-feature` 在實作前的可選需求訪談。核心目標是逐一解決會改變功能結果或交付風險的決策；不要把可查證的事實轉嫁給使用者。

## 1. 啟用邊界

每次觸發 `add-new-feature` 時，先提出一個不計入訪談題數的啟用問題：

> 是否進入 Grill Me 需求釐清模式？建議進入，以便在開發前逐一確認需求與風險；若要略過，請明確表示「跳過 Grill Me」。

- `OK`、`Yes`、「可以」或其他明確同意語意：啟用模式。
- 「跳過 Grill Me」、「這次不要需求訪談，直接進入標準流程」、「Skip the discovery gate for this work item」或同等明確語意：只對當次 Work Item 略過。
- 「開始吧」、「照常處理」、「不用問了」或「你決定」：語意不足，詢問是否要啟用或明確跳過。
- 「開始實作」、「直接開發」或其他同時明確要求停止訪談並開始實作的語意：依「提前開始與風險承擔」處理。

略過模式不會取消標準流程的停止條件。Acceptance Criteria 衝突、資安、敏感資料、不可逆遷移、重大架構取捨或正式環境風險仍須取得決策。

## 2. 訪談規則

啟用後遵守以下規則：

1. 一次只提出一個決策問題，等待回覆後才繼續。
2. 每題先提供建議答案與簡短理由；必要時說明主要取捨。
3. 回答模糊、不完整或與先前決策衝突時，停留在同一分支，指出缺口後提出一個更窄的問題。
4. 未解決上游決策前，不提前詢問依賴它的下游細節。
5. 不為了湊清單詢問不適用的問題。
6. 不把使用者的沈默、含糊肯定或委派語意當成跳過、風險承擔或開發授權。

### 唯讀探索

提出問題前，先查找能從環境取得的事實：

- 讀取相關程式碼、文件、設定、現有測試與 Git 歷史。
- 讀取已在任務範圍內的外部資料；必要時查閱官方技術文件。
- 不修改檔案、不建立 branch 或 worktree、不安裝依賴、不執行會改變資料或外部系統的操作。
- 找不到的事實標記為未知；只有當未知內容需要使用者決策時才提出問題，不得猜測成既定事實。

## 3. 題數上限

- 啟用問題不計入題數；啟用後的每一個決策問題都計數。
- 預設上限為 20 題，最終共同理解核准問題也計入。
- 若能在上限內完成，先展示共同理解摘要，再把核准作為最後一題。
- 若第 19 題後仍有未解決分支，第 20 題列出未決事項，提出足以完成訪談的具體新上限，並詢問是否同意延長。
- 未取得延長同意時，不得提出第 21 題，也不得因達到上限而自動開始實作。

## 4. 決策順序

依答案動態展開，通常按照以下依賴順序：

1. 目標、問題與成功定義。
2. 使用者、角色與使用情境。
3. 範圍內、範圍外與不可改變的行為。
4. 核心流程、狀態、錯誤與邊界情況。
5. UI/UX、響應式與可及性。
6. 資料模型、權限、安全、整合與外部契約。
7. 相容性、效能、可觀測性與營運限制。
8. Acceptance Criteria、測試與品質門檻。
9. 遷移、發布、回滾與交接。

維護訪談覆蓋表。每個適用面向都必須標記為：

- 已由環境確認。
- 已由使用者決定。
- 不適用。
- 未解決。

只要仍有「未解決」，就不可宣告共同理解完成。覆蓋表是訪談控制工具；Project Task 只保存有效決策，不需要列出大量不適用項目。

## 5. 自主決策邊界

以下問題必須由使用者決定：

- 可觀察的產品行為、範圍或 Acceptance Criteria。
- 資料、權限、安全、隱私或外部契約。
- 重大或難以逆轉的架構與資料遷移。
- 會顯著改變交付風險的相容性、發布或回滾方案。

符合已核准規格、可逆且不改變外部行為的實作細節，可依專案慣例自行決定並記錄，例如內部命名、小型重構方式或等價的測試組織。

若使用者偏好與既有規格、架構限制或安全規則衝突：

1. 提供查到的依據。
2. 說明衝突及其下游影響。
3. 提出一個可行的建議答案。
4. 停留在該分支等待決定。

規格可在明確決策後變更；不可違反的安全、法規或平台限制只能選擇合規替代方案。

## 6. 提前開始與風險承擔

使用者在訪談中明確要求「開始實作」或同等語意時：

1. 停止提出一般需求問題。
2. 彙整仍未解決的假設與風險，逐項說明觸發條件、可能後果與可用的降低方式。
3. 一般、可逆風險只需告知並在 Project Task 記錄，不要繼續追問。
4. 涉及資料損失、資安、權限、法規、不可逆變更或正式環境的重大風險時，把所有風險逐項列明，再用一個問題取得整體、明確的風險承擔同意。
5. 未取得重大風險承擔同意前不得執行受影響工作；取得後依可逆且風險最低的方案推進。

提前開始、風險告知及承擔結果只對當次 Work Item 有效，並在 Project Task 留存。

## 7. 共同理解與解鎖

所有適用分支解決後，展示共同理解摘要：

```markdown
## Shared Understanding

- Objective:
- Users and scenarios:
- Core behavior and states:
- In scope:
- Out of scope:
- Acceptance Criteria:
- Key decisions and constraints:
- Assumptions:
- Risks and mitigations:
- Unresolved questions: None
```

接著單獨詢問：

> 是否確認以上共同理解並授權開始實作？

只有在這個最終核准問題的上下文中，`OK`、`Yes`、「可以」或更明確的核准語意才解除閘門。若使用者修正摘要，重新開啟受影響的決策分支。

解鎖後：

- 在 Project Task 的 `Discovery / Shared Understanding` 記錄模式、核准狀態、摘要、重要決策、假設與風險。
- 把可執行的產品與技術結論同步至 System Spec、Scope 與 Acceptance Criteria。
- 若模式被明確略過，記錄略過指示、未驗證假設與已知風險。

## 8. 實作期間重新上鎖

實作期間若發現新資訊會改變產品行為、範圍、Acceptance Criteria、資料與權限、外部契約、重大架構或發布風險：

1. 停止受影響的實作，不擴大到不受影響的工作。
2. 回到對應決策分支，一次只問一題。
3. 更新共同理解與 Project Task 決策紀錄。
4. 取得對變更部分的核准後再繼續。

## 9. Hotfix

Hotfix 不可自動跳過閘門，但使用縮短分支，只處理事故影響、重現條件、最小修正範圍、不可改變的行為、驗證方式與回滾方案。只有使用者對當次 Work Item 明確跳過時才略過；重大風險與標準 Hotfix 停止條件仍然有效。
